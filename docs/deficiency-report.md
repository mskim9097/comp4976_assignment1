# Assignment 1 deficiency resolution report (COMP4976)

Source of the issues: the instructor's marking feedback for Assignment 1 (94% with bonus; deductions listed first), plus quality problems we found ourselves while rebuilding the application. The first block was also fixed in the Assignment 1 code (merged on 2026-11-12) and then carried over into the new architecture.

## Issues named in the instructor's feedback

| Issue | Original problem | Resolution |
|---|---|---|
| Authorization: Pitt Meadows admin should only see their own municipality and candidates (-3) | The admin screens were scoped, but the public pages (home, positions, candidate directory, details) ignored who was logged in, so a municipality admin saw every municipality there. | Multi-tenancy is now part of the data model: `Position`, `Candidate` and `ApplicationUser` have a `MunicipalityId`. EF Core query filters limit every query to the tenant of the request. The Api (`TenantScopeFilter`) answers 403 for another municipality's administrator and 404 for ids of another tenant. The Admin app runs every operation in a scope restricted to the tenant in the login cookie. The public site shows one municipality per URL (`/burnaby`) and asks the Api only for `/api/{slug}/...`. Checked by hand in the browser and with curl: `burnabyadmin` sees only the rows of Burnaby and gets "not found" or 403 for Surrey ids. |
| Voting guide: a visitor cannot choose candidates from multiple cities (-2) | The browser list accepted candidates of any municipality, so one printed guide could mix cities. | One guide per browser tab (`sessionStorage` key `mems.guide`). The first choice fixes the municipality; a candidate of another municipality is refused with a message (`SelectionRules.CheckAdd`). |
| Voting guide: a visitor cannot choose more than one mayor (-2) | No limit per position. | A position accepts at most `SeatsAvailable` choices (Mayor 1, Councillor 8, ...). The rule is in `MEMS.Shared` so the Blazor site and the iOS app share it. |
| Admins should not have the option to short list candidates (-2) | The "add to preferred candidates" tools were also shown to logged-in administrators. | Administrators use the separate Admin app, which has no voter tools; the public site has no administrator features. Voters' choices live only in their own browser. |
| Source ZIP not found in the D2L folder (-1) | The archive could not be confirmed in the submission folder. | Submission checklist in the README: build the zip from `main`, re-download it from D2L and compare it with the local file (done for Assignment 1 and repeated for Assignment 2). |

## Problems we found ourselves

| Issue | Original problem | Resolution |
|---|---|---|
| Authorization model | One Identity role per municipality ("Pitt Meadows Admin") matched by name; nothing tied an administrator to exactly one tenant. | Two roles (`Super Admin`, `Municipality Admin`); a Municipality Admin has exactly one `MunicipalityId`, carried in the JWT and in the Admin login cookie. |
| Data integrity | A candidate's municipality was only reachable through its position, and nothing stopped the two from disagreeing; seats could be 0. | Composite foreign key `(PositionId, MunicipalityId)`, `CHECK` on seats (1-100), unique indexes for municipality name and slug and for the position name per municipality, case-insensitive duplicate checks in the services. |
| Missing validation | Validation lived in MVC view models; the Web API repeated part of it. | One set of request classes with DataAnnotations in `MEMS.Shared` used by the Blazor forms (client), the Api (server) and checked again in the services; constraints in SQL Server (database layer). |
| Security | The API login had no lockout, so passwords could be guessed without limit; failed logins were not logged. | Accounts are locked for 5 minutes after 5 failed logins (API and Admin app), failed logins and tenant violations are written to the structured log, the Admin app refuses accounts without an administrator role, and the voting choices are never sent to a server. |
| Error handling and logging | Errors were handled per action (catch and message); there was no global handler and no central logging view. | `ApiExceptionHandler` (global handler: 400/403/404/409 problem details, general 500 message without internals), friendly messages in the Admin app, structured logs, traces and health checks in the Aspire dashboard. |
| Code quality | Business rules (duplicate checks, province list, image handling) were inside MVC controllers; SQLite database. | Service layer in `MEMS.Data`, thin controllers, shared rules in `MEMS.Shared`, SQL Server with EF Core migrations, Copilot instruction, prompt and skill files updated for the new solution. |
| Incomplete requirement of the new assignment | Public site was an MVC page with `localStorage`. | Blazor WebAssembly site, tenant from the URL, data only through the Api, voting choices only in `sessionStorage` (never sent to the Api, never in SQL Server). |
