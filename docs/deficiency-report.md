# Assignment 1 deficiency resolution report (COMP4976)

Source of the issues: the instructor's marking feedback for Assignment 1 (94% with bonus; deductions listed first), plus problems we found ourselves while rebuilding the application. The first block was also fixed in the Assignment 1 code (merged on 2026-11-12) and then carried over into the new architecture.

## Issues named in the instructor's feedback

| Issue | Original problem | Resolution |
|---|---|---|
| Authorization: Pitt Meadows admin should only see their own municipality and candidates (-3) | The admin screens were scoped. The public pages (home, positions, candidate directory, details) ignored who was logged in, so a municipality admin saw every municipality there. | Multi-tenancy is part of the data model: `Position`, `Candidate` and `ApplicationUser` have a `MunicipalityId`. EF Core query filters limit every query to the tenant of the request. The Api (`TenantScopeFilter`) answers 403 for the administrator of another municipality and 404 for ids of another tenant. The Admin app runs every operation in a scope limited to the tenant in the login cookie. The public site shows one municipality per URL (`/burnaby`) and asks the Api only for `/api/{slug}/...`. Checked in the browser and with curl: `burnabyadmin` sees only Burnaby rows and gets 404 or 403 for Surrey ids. |
| Voting guide: a visitor cannot choose candidates from multiple cities (-2) | The browser list accepted candidates of any municipality, so one printed guide could mix cities. | One guide per browser tab (`sessionStorage` key `mems.guide`). The first choice sets the municipality. A candidate of another municipality is refused with a message (`SelectionRules.CheckAdd`). |
| Voting guide: a visitor cannot choose more than one mayor (-2) | There was no limit per position. | A position accepts at most `SeatsAvailable` choices (Mayor 1, Councillor 8, ...). The rule is in `MEMS.Shared`, so the Blazor site and the iOS app use the same rule. |
| Admins should not have the option to short list candidates (-2) | The "add to preferred candidates" tools were also shown to logged-in administrators. | Administrators use the separate Admin app, which has no voter tools. The public site has no administrator features. The choices of a voter stay in the browser of that voter. |
| Source ZIP not found in the D2L folder (-1) | The archive could not be confirmed in the submission folder. | The README has a submission checklist: build the zips from `main`, then download them again from D2L and compare them with the local files. |

## Problems we found ourselves

| Issue | Original problem | Resolution |
|---|---|---|
| Authorization model | There was one Identity role per municipality ("Pitt Meadows Admin"), found by name. Nothing tied an administrator to exactly one tenant. | There are two roles (`Super Admin`, `Municipality Admin`). A Municipality Admin has exactly one `MunicipalityId`. It is carried in the JWT and in the Admin login cookie. |
| Data integrity | The municipality of a candidate was only reachable through its position. Nothing stopped the two from disagreeing. Seats could be 0. | A composite foreign key `(PositionId, MunicipalityId)`. A `CHECK` on seats (1-100). Unique indexes for the municipality name and slug and for the position name per municipality. Case-insensitive duplicate checks in the services. |
| Missing validation | Validation lived in MVC view models. The Web API repeated only part of it. | One set of request classes with DataAnnotations in `MEMS.Shared`. The Blazor forms (client), the Api (server) and the services all use it. SQL Server has its own constraints (database layer). Websites must start with `http://` or `https://`. |
| Security | The API login had no lockout, so passwords could be guessed without limit. Failed logins were not logged. | Accounts are locked for 5 minutes after 5 failed logins (API and Admin app). Failed logins and tenant violations go to the structured log. The Admin app refuses accounts without an administrator role. Voting choices are never sent to a server. |
| Error handling and logging | Each action handled its own errors. There was no global handler and no central view of the logs. | `ApiExceptionHandler` is the global handler (400/403/404/409 problem details and a general 500 message without internals). The Admin app shows friendly messages. Logs, traces and health checks are in the Aspire dashboard. |
| Code quality | Business rules (duplicate checks, province list, image handling) were inside MVC controllers. The database was SQLite. | A service layer in `MEMS.Data`, thin controllers, shared rules in `MEMS.Shared` and SQL Server with EF Core migrations. The Copilot instruction, prompt and skill files were rewritten for the new solution. |
| Incomplete requirement of the new assignment | The public site was an MVC page that used `localStorage`. | A Blazor WebAssembly site. The tenant comes from the URL, data comes only through the Api, and voting choices stay in `sessionStorage` (never sent to the Api, never in SQL Server). |
